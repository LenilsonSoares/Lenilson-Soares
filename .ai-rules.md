# Senior Workflow Rules

Use este arquivo como regra base para qualquer IA que for ajudar neste repositório.
O objetivo é gerar código seguro, simples, organizado e econômico em tokens.

## Perfil do projeto

- Tipo de projeto: bot.
- Prioridade: segurança, clareza, manutenção e baixo custo de execução.
- Estilo esperado: código direto, modular e fácil de evoluir.
- Evitar: soluções grandes demais, abstrações prematuras, duplicação e respostas longas sem necessidade.

## Princípios obrigatórios

### 1. Clean Architecture

- Separar regras de negócio de detalhes externos.
- Não misturar lógica principal com banco de dados, APIs, mensagens, UI ou bibliotecas.
- Organizar o código por responsabilidade, não por improviso.
- Criar módulos pequenos e com nomes claros.
- Manter dependências apontando para o núcleo do sistema, nunca o contrário.

Camadas recomendadas:

- `domain`: regras principais, entidades e validações de negócio.
- `use-cases`: ações que o bot executa.
- `infra`: banco de dados, APIs externas, filas, logs e integrações.
- `interfaces`: handlers, comandos, rotas, controllers ou adaptadores.
- `config`: variáveis de ambiente, inicialização e dependências.

### 2. Defensive Programming

- Validar entradas antes de processar.
- Tratar erros previsíveis com mensagens claras.
- Nunca confiar em dados recebidos de usuários, APIs ou banco.
- Proteger tokens, chaves e dados sensíveis.
- Usar variáveis de ambiente para segredos.
- Evitar logs com senhas, tokens, documentos, emails privados ou dados sensíveis.
- Criar limites para evitar abuso, spam, loops infinitos e consumo excessivo.
- Falhar de forma segura quando algo inesperado acontecer.

Checklist de segurança antes de finalizar código:

- Entradas foram validadas?
- Segredos ficaram fora do código?
- Erros foram tratados?
- Logs não vazam dados sensíveis?
- O código evita loops, retries infinitos ou chamadas desnecessárias?
- Existe fallback seguro quando serviço externo falha?

### 3. KISS

- Escolher a solução mais simples que resolva o problema real.
- Evitar frameworks, bibliotecas e padrões sem necessidade.
- Não criar abstração antes de existir repetição ou complexidade real.
- Preferir funções pequenas e nomes explícitos.
- Escrever menos código quando isso melhora a clareza.
- Remover código morto, comentários óbvios e arquivos sem função.

Regra prática:

- Se uma solução simples resolve bem, não criar uma solução sofisticada.
- Se uma função está difícil de explicar, ela provavelmente precisa ser dividida.
- Se uma dependência não é essencial, não adicionar.

## Economia de tokens

Ao responder ou gerar código:

- Ser direto e evitar explicações repetidas.
- Mostrar apenas os arquivos alterados ou trechos relevantes.
- Não reescrever arquivos inteiros quando uma alteração pequena basta.
- Preferir listas curtas, decisões objetivas e passos acionáveis.
- Antes de implementar, ler o contexto existente do projeto.
- Não sugerir refatorações fora do escopo pedido.

Formato ideal de resposta:

1. O que será feito.
2. Arquivos que serão alterados.
3. Código ou patch necessário.
4. Como testar.

## Regra de implementação

Antes de escrever código:

- Entender o objetivo do bot.
- Identificar entradas, saídas e riscos.
- Definir o fluxo principal.
- Escolher a menor arquitetura suficiente.
- Confirmar onde a regra de negócio deve ficar.

Durante a implementação:

- Criar código modular.
- Evitar duplicação.
- Validar dados nas bordas do sistema.
- Manter nomes claros.
- Usar tratamento de erro consistente.
- Escrever testes quando houver regra de negócio ou risco de regressão.

Depois da implementação:

- Revisar segurança.
- Revisar simplicidade.
- Revisar organização.
- Remover código desnecessário.
- Explicar como rodar ou testar.

## Padrão para bots

Todo bot deve ter:

- Comandos ou eventos bem separados.
- Validação das mensagens recebidas.
- Tratamento de erro por comando ou fluxo.
- Controle contra spam ou chamadas repetidas.
- Configuração por ambiente.
- Logs úteis, sem dados sensíveis.
- Fluxos pequenos e fáceis de testar.

Evitar:

- Um único arquivo gigante com tudo dentro.
- Regras de negócio dentro do handler da plataforma.
- Chaves de API no código.
- Mensagens duplicadas em vários lugares.
- Integrações externas chamadas diretamente em qualquer parte do projeto.

## Prompt padrão para usar com IA

Use este prompt quando pedir novas funcionalidades:

```text
Codex, implemente esta funcionalidade seguindo o .ai-rules.md.

Objetivo:
[descreva o que o bot precisa fazer]

Entrada:
[descreva o que o usuário envia]

Saída esperada:
[descreva o que o bot responde ou executa]

Regras de segurança:
[liste limites, validações e dados sensíveis]

Restrições:
- Use Clean Architecture quando fizer sentido.
- Use Defensive Programming nas bordas do sistema.
- Use KISS para evitar complexidade desnecessária.
- Economize tokens e mostre apenas o necessário.
```

## Definição de pronto

Uma tarefa só está pronta quando:

- Resolve o problema pedido.
- Está simples de entender.
- Não expõe segredos.
- Trata erros principais.
- Tem organização mínima por responsabilidade.
- Pode ser testada ou validada.
- Não adiciona complexidade desnecessária.
